# SOLID reading of `src/products`

> Based on `docs/Workshop.md` and the current `src/products` implementation.

## Short answer

No — `src/products` is **not SOLID** right now. It is an anemic, god-object CRUD module: one `Product` model carries
catalog, stock, supplier, pricing and warehouse data, and one `ProductService` does validation, persistence, stock
reservation and tax-aware pricing.

## Per-principle read

### Single Responsibility Principle (SRP) — **violated**

- `ProductService` (`src/products/product.service.ts`) handles input validation, persistence, stock reservation,
  regional pricing and query filtering.
- The `Product` model in `prisma/schema.prisma` is explicitly a “God model” mixing catalog, stock, supplier/pricing and
  warehouse concerns.
- `ProductsController` (`src/products/products.controller.ts`) both parses the request body and delegates.
- `CreateProductSchema` (`src/products/create-product.schema.ts`) documents the smell: “One big schema mirroring the God
  `Product` model column-for-column”.

### Open/Closed Principle (OCP) — **violated**

- The regional margin table is a hard-coded `Record` in `src/products/product.service.ts`. Adding a new region or
  pricing strategy means editing the service.
- `CreateProductSchema` is a single monolithic shape; new product kinds cannot be introduced without touching the
  schema.

### Liskov Substitution Principle (LSP) — **not applicable**

There is no inheritance or subtype hierarchy in `src/products`, so LSP has nothing to substitute. The `unknown` body
cast and `as` casts in the service are type-safety smells, not LSP violations.

### Interface Segregation Principle (ISP) — **violated / absent**

- The only “interfaces” are data shapes: `CreateProductInput` and `SupplierRegionInfo`. They are broad and bundled.
- `ProductService` is a single concrete class with many methods, so any consumer depending on it depends on the whole
  surface.

### Dependency Inversion Principle (DIP) — **violated**

- `ProductsController` depends directly on the concrete `ProductService`.
- `ProductService` depends directly on the concrete `PrismaService` and on `Product` from `@prisma/client`.
- NestJS DI is present, but there are no domain ports, repository interfaces or Prisma adapter, so the domain layer is
  not decoupled from infrastructure.

## Do SOLID principles apply here?

**Yes**, but they are not the only or the best lens. SOLID is still relevant for a NestJS web app:

- **SRP** maps to thin controllers and focused use-case / domain services.
- **DIP** maps to repository interfaces in the domain and Prisma adapters in infrastructure.
- **OCP** matters the moment the app has real variability such as pricing rules, regions or product types.
- **LSP/ISP** matter when the code uses class hierarchies or role interfaces.

## Do they make sense for a web app like this one?

Yes, but **pragmatically**. The current design is at the *other* extreme from SOLID, which is why it is hard to test and
extend. `Workshop.md` deliberately starts from this legacy state and targets CUTE DDD / CUPID instead — bounded
contexts, aggregates, value objects, ports-and-adapters and small domain services. That target design would satisfy
SOLID as a side effect, while also giving the codebase a domain language and strong testability.

So: **SOLID is a useful guardrail**, but the more urgent problem in `src/products` is the **anemic, god-object domain
model**.

# Solving the ISP / DSP on the Service only

## Problem Statement

`ProductService` was originally a monolithic concrete class exposing the entire surface of product operations to every
consumer:

- Catalog creation (`create`)
- Catalog querying (`findAll`, `findOne`)
- Inventory operations (`reserveStock`)
- Pricing & Tax calculations (`calculateResellerPrice`)

Any consumer (such as `ProductsController` or future background jobs/services) had to depend on the entire concrete
`ProductService` class, violating:

1. **Interface Segregation Principle (ISP)**: Clients are forced to depend on methods they do not use.
2. **Dependency Inversion Principle (DIP/DSP)**: Consumers depended on a concrete implementation rather than
   abstractions/interfaces.

## Refactoring Plan & Progression

- [x] **Step 1: Extract role-specific interfaces** (following CLAUDE.md: one interface per file):
  - `ProductCreator` (`src/products/product-creator.ts`) — handles creation of catalog items
  - `ProductReader` (`src/products/product-reader.ts`) — handles querying products (`findAll`, `findOne`)
  - `StockReserver` (`src/products/stock-reserver.ts`) — handles stock reservation
  - `ResellerPriceCalculator` (`src/products/reseller-price-calculator.ts`) — handles regional reseller price
    calculation
- [x] **Step 2: Implement interfaces in `ProductService`**:
  - `ProductService implements ProductCreator, ProductReader, StockReserver, ResellerPriceCalculator`
- [x] **Step 3: Update `ProductsController` & `ProductsModule`**:
  - `ProductsModule` provides injection tokens (`PRODUCT_CREATOR`, `PRODUCT_READER`, `STOCK_RESERVER`,
    `RESELLER_PRICE_CALCULATOR`) mapped to `ProductService`
  - `ProductsController` injects discrete segregated interfaces instead of the concrete `ProductService`
- [x] **Step 4: Update Unit & E2E Tests**:
  - `products.controller.spec.ts` mocks each segregated interface independently
  - `product.service.spec.ts` tests `ProductService` implementation
  - All tests passing

## Result

1. **Interface Segregation Principle (ISP)**: Consumers only depend on the narrow slice of behavior they actually
   consume (e.g. `StockReserver` for inventory workflows, `ResellerPriceCalculator` for pricing queries).
2. **Dependency Inversion Principle (DIP/DSP)**: Consumers depend on interface abstractions and injection tokens rather
   than the concrete `ProductService` class.
3. **CLAUDE.md Compliance**: Each interface and its token live in a dedicated file matching the type name.

# Conclusion: Why SOLID Principles Are Not Enough for Clean Code Quality

While SOLID principles offer valuable structural guidelines for object-oriented design, this refactoring highlights why
**SOLID alone is insufficient** as a code quality and engineering process.

### 1. Syntactic Compliance vs. Domain Reality (Anemic Models)

You can satisfy every SOLID letter—creating perfectly segregated interfaces, thin single-responsibility classes, and
inverted dependencies—while the underlying domain remains completely broken:

- A `Product` entity can still be an anemic God table littered with primitive types (`priceTaxRate: 900`, invalid
  currencies, or negative stock).
- SOLID tells you *must separate things*, but not *what the domain boundaries, aggregates, or ubiquitous language
  actually are*.

### 2. The Illusion of Test Coverage vs. Mutation Testing

Following SOLID often leads to high line and branch coverage purely by mocking interfaces and asserting delegation
(e.g., `expect(creator.create).toHaveBeenCalled()`).

- However, our **mutation test baseline with Stryker** demonstrated that **57% of mutants survived** despite passing
  test suites.
- Critical boundary conditions (e.g., `product.stock < quantity` vs `<=`, missing input validations, or silent default
  fallbacks) slip through SOLID architectures when tests only assert structural interactions rather than behavioral
  invariants.

### 3. Structural Proliferation without Cohesion

Dogmatic adherence to SOLID in isolation leads to "interface explosion" and accidental complexity:

- Splitting every class and extracting every interface on top of a database-centric data model adds layers of
  indirection without improving business clarity.
- True cohesion comes from aligning code with business subdomains and bounded contexts, not merely cutting files into
  smaller mechanical pieces.

### 4. Beyond SOLID: The Holistic Quality Stack

A complete code quality process requires complementary practices:

- **Domain-Driven Design (DDD)**: To establish Ubiquitous Language, explicit Bounded Contexts, Always-Valid Entities,
  and Value Objects that eliminate primitive obsession.
- **CUPID Properties**: Favoring Joyful, Composable, Predictable, Idiomatic, and Domain-based code over rigid checklist
  compliance.
- **Robust Quality Engineering**: Combining TDD with **Mutation Testing** (Stryker) and Property-Based Testing to ensure
  the test suite genuinely guards business invariants.
