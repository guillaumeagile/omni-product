## How the walk continues: from CUPID to (FP + DDD) fellowship

This is where the thinking started, and it is worth retracing the steps before writing any code.

CUPID gave us **properties**, not rules — directions of travel rather than pass/fail gates. But when we held each
property against the list of gaps above, every one of them pointed *beyond* CUPID toward two older traditions:

- **Composable** and **Unix philosophy** then follow almost for free: small value objects and pure functions compose by
  nature; splitting the God schema by concern is exactly "one thing well".

- **Predictable** asked: how do we make failure visible and invalid states impossible? The answer was not more
  discipline — it was *functional* machinery: errors as values (`Result`), discriminated unions, pure decisions with
  effects pushed to the edge.
- **Idiomatic** asked: how do we do all this *in TypeScript*, without importing a foreign philosophy? The answer was
  TS-native algebraic design first, libraries only when the team wants their whole style.

- **Domain-based** asked: what should the types be *about*? The answer was not better naming conventions — it was *DDD
  tactical* machinery: value objects, branded types, aggregates that protect invariants, one model per bounded context
  instead of one God schema.

So the insight was: **FP and DDD are not two extra methodologies stacked on top of CUPID — they are what CUPID resolves
into when you push each property to its logical conclusion.** FP supplies the *how* (the mechanics that make code
predictable and composable); DDD supplies the *what* (the concepts the types should express). CUPID is the compass that
told us which way to walk.

That walk is written down in two documents, meant to be read in order:

- `4.the FP idiomatic way.md` — the **mechanics**: how to be predictable and idiomatic in TypeScript (unions, `Result`,
  smart constructors, effects at the edge, and when a library is worth its cost)
- `5.the FP fellowship.md` — the **synthesis**: the FP habits assembled as companions and mapped one-by-one onto
  tactical DDD patterns, ending at the quest — a use case signature that reads as a complete, honest business rule

The refactoring game that follows replays this same walk in code: each gap listed at the top of this document gets
closed by one FP habit serving one DDD pattern, guided by one CUPID property.
