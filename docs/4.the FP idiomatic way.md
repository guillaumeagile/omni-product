# The FP idiomatic way

> Skill: design TypeScript + NestJS code so **illegal states are unrepresentable**, pure decisions stay composable, and
> side effects happen as late as possible.

## Short answer

If the question is _“should we make our own `Result<T, E>` / `DomainError`, or should we use an existing library?”_, the
pragmatic answer for most NestJS teams is:

- make your **own small FP core** first
- use **TypeScript-native** constructs before adding a framework
- introduce a library only if the team wants its whole style, not just one type

In practice:

- **No library** is the most idiomatic default for a typical TypeScript/NestJS team
- **`neverthrow`** is the easiest library to adopt if you want a ready-made `Result`
- **`fp-ts`** is powerful but expensive to learn and usually too abstract for a CRUD-to-DDD migration
- **`effect`** is excellent, but it is an architectural choice, not a small utility

## Why this matters

CUPID pushes toward code that is:

- composable
- predictable
- domain-oriented
- easy to test

The FP reading of that is:

- **pipe operations left to right**
- **keep data honest**
- **push effects to the edge**
- **make invalid states impossible, or at least explicit**

That motto is stronger than “handle errors nicely”. It means the main job of the model is to prevent nonsense from
existing in the first place.

## The skill

### 1. Model the domain in the type system first

Prefer types that encode truth over services that keep re-checking everything at runtime.

Reach first for:

- discriminated unions
- readonly data
- opaque/branded scalar types
- value-specific constructors
- small object types per concept
- mapped types and conditional types to derive safe variants

Good examples of the mindset:

- a product is not “an object with many optional fields”; it is one of several legal product shapes
- stock quantity is not “just a number”; it is a quantity that cannot be negative
- published and draft entities are not the same type if their invariants differ

Typical TypeScript-native tools:

```ts
type DraftProduct = {
    kind: 'draft';
    name: string;
};

type PublishedProduct = {
    kind: 'published';
    id: ProductId;
    name: ProductName;
    price: Money;
};

type ProductState = DraftProduct | PublishedProduct;
```

Use the type system to make nonsense hard to express.

### 2. Represent absence and failure explicitly

A useful rule is:

- **absence** is not the same thing as **failure**
- **expected business failure** is not the same thing as **unexpected defect**

That gives three distinct tools:

- **`Option<T>`** or `T | undefined` for absence
- **`Result<T, E>`** for expected domain or application failures
- **exceptions** for defects, infrastructure outages, and unrecoverable framework failures

For DDD in NestJS, this is a good split:

- controller or pipe: parse and decode input
- use case: return `Result<T, DomainError>`
- domain: pure functions and pure decisions
- infrastructure: perform effects; let unexpected failures throw

### 3. Prefer tagged domain errors over class hierarchies

In TypeScript, discriminated unions are usually more idiomatic than large inheritance trees.

Prefer:

```ts
type ReserveStockError =
    | { kind: 'ProductNotFound'; productId: ProductId }
    | { kind: 'QuantityMustBePositive'; quantity: number }
    | { kind: 'InsufficientStock'; available: number; requested: number };
```

Over:

```ts
class DomainError extends Error {}
class ProductNotFoundError extends DomainError {}
class InsufficientStockError extends DomainError {}
```

Why unions fit TypeScript well:

- exhaustive `switch` handling
- easy serialization
- no fragile `instanceof` checks
- clearer mapping to HTTP, logs, and tests

If a real class gives domain behavior, use a class. If it is just data, a tagged object is usually better.

### 4. Keep NestJS at the boundary

NestJS is a delivery mechanism, not the domain.

That means:

- controllers should decode HTTP concerns
- use cases should orchestrate domain logic
- domain code should not know `BadRequestException`, `NotFoundException`, or Prisma types
- HTTP mapping should happen once, near the edge

A healthy flow looks like:

```text
HTTP request
-> zod safeParse
-> map DTO to command
-> use case returns Result
-> controller maps DomainError to HTTP response
-> framework serializes output
```

This keeps the core portable and testable.

### 5. Put effects at the end of the pipe

A predictable application does not interleave business decisions with database writes and transport exceptions.

Prefer a sequence like:

```text
parse
-> normalize
-> validate invariants
-> load required data
-> decide
-> persist
-> publish integration event
```

The earlier stages should be as pure as possible.

A simple heuristic:

- if a function can be pure, keep it pure
- if a function must perform I/O, make that obvious in its signature and location
- if you can decide before touching the database, do that first

### 6. Use `Result` as a small protocol, not a philosophy

A `Result` type is helpful because it lets you say:

- this use case can succeed with `T`
- or fail with one of these expected errors

That is already enough for most business code.

A small homegrown shape is sufficient:

```ts
type Result<T, E> =
    | { ok: true; value: T }
    | { ok: false; error: E };
```

Add only a few helpers if they improve readability:

- `ok(value)`
- `err(error)`
- `map(result, fn)`
- `andThen(result, fn)`
- `match(result, branches)`

Do not build a mini-fp-ts unless the team truly wants that.

### 7. Use TypeScript’s type transformations as design tools

TypeScript gives you enough native machinery to design precise workflows.

Useful standard tools:

- `Readonly<T>`
- `Partial<T>`
- `Required<T>`
- `Pick<T, K>`
- `Omit<T, K>`
- `Extract<T, U>`
- `Exclude<T, U>`

Useful custom patterns:

- “persisted vs new” entities
- “command vs read model” projections
- “legal patch shape” types
- “state-dependent fields” through unions

Examples:

```ts
type New<T> = Omit<T, 'id' | 'createdAt' | 'updatedAt'>;
type Persisted<T> = T & Readonly<{ id: string; createdAt: Date; updatedAt: Date }>;

type CommandOf<T> = {
    [K in keyof T as T[K] extends Function ? never : K]: T[K];
};
```

The point is not cleverness. The point is to remove duplication and encode constraints once.

### 8. Separate boundary validation from domain invariants

This distinction is essential.

Boundary validation answers:

- is the payload shaped correctly?
- are required fields present?
- are numbers actually numbers?

Domain validation answers:

- is this a legal price?
- can this state transition happen?
- does this product kind allow this field combination?

So:

- use **Zod** for transport shape validation
- use **constructors / smart constructors / pure domain functions** for business invariants
- use `safeParse`, not exception-based control flow, for expected invalid input

A system becomes clearer when the DTO is not pretending to be the domain.

### 9. Prefer state machines over boolean soup

If an entity has a lifecycle, model the lifecycle.

Avoid:

- `isPublished`
- `isArchived`
- `isDeleted`
- `isPendingApproval`

Those combinations create nonsense.

Prefer:

```ts
type ProductStatus =
    | { kind: 'Draft' }
    | { kind: 'Active'; activatedAt: Date }
    | { kind: 'Archived'; archivedAt: Date; reason: string };
```

Now impossible combinations disappear by construction.

### 10. Keep infrastructure types from leaking inward

Prisma models, HTTP DTOs, and queue payloads are not automatically your domain model.

Prefer explicit mapping:

- DTO -> command
- database row -> domain snapshot or aggregate state
- domain event -> integration event payload

When infra types leak everywhere:

- refactors become expensive
- domain language disappears
- tests become coupled to tools instead of behavior

## Learning effort of existing libraries

### `neverthrow`

**Effort:** low

Good when:

- the team wants a ready-made `Result`
- you want a light functional vocabulary without a new runtime model
- most developers are application developers, not FP specialists

What the team needs to learn:

- `ok` / `err`
- `map`
- `andThen`
- `match`
- async variants if used

Main risk:

- the library type can spread everywhere even though the app only needed a tiny subset

Verdict:

- the best off-the-shelf option if you do not want to write your own small `Result`

### `fp-ts`

**Effort:** high

Good when:

- the team already thinks in algebraic data types and typed composition
- you want a larger functional toolkit, not just `Result`

What the team needs to learn:

- `Either`, `Option`, `TaskEither`, `ReaderTaskEither`
- higher-kinded type style conventions
- pipe-based combinator-heavy design
- ecosystem idioms and naming

Main risks:

- steeper onboarding
- reduced readability for teams unfamiliar with functional programming
- library-driven architecture rather than domain-driven architecture

Verdict:

- strong tool, weak default for a typical NestJS team

### `effect`

**Effort:** high to very high

Good when:

- you want one coherent model for effects, dependency injection, concurrency, retries, resources, and failure
- the team is willing to adopt a real platform style

What the team needs to learn:

- the `Effect` model itself
- typed services / contexts
- layers, scopes, resources, structured concurrency
- new testing and composition idioms

Main risks:

- large conceptual shift
- best payoff comes when adopted broadly, not piecemeal

Verdict:

- excellent if chosen intentionally, excessive if the real need is just `Result<T, E>`

## Recommendation ladder for a NestJS team

### Level 1 — TypeScript-native only

Use:

- discriminated unions
- opaque scalar types
- smart constructors
- a tiny local `Result`
- `safeParse` at boundaries
- explicit mappers between layers

This gives most of the value with the least learning cost.

### Level 2 — Add `neverthrow` if the team wants ergonomics

Use it when:

- the team likes the pattern
- people want standard helpers
- the codebase is already leaning functional

This is a reasonable compromise.

### Level 3 — Adopt `effect` only if you want a new application model

Use it when:

- the team wants typed effects as a first-class architectural principle
- you are willing to train the team and standardize around it

Do not adopt it just to avoid writing a `Result` type.

## Practical rules for this repo shape

For a NestJS + Prisma + Zod application like this one:

- use `safeParse` in controllers or pipes
- turn DTOs into commands, not directly into domain objects
- let use cases return `Result<Success, DomainError>` for expected business outcomes
- map domain errors to Nest HTTP exceptions at the boundary
- let unexpected infrastructure failures crash into the global exception layer
- keep pricing, stock, and product invariants in pure domain code where possible

## Smells that usually mean the design is not FP-idiomatic

- one large DTO equals one large domain model
- many optional fields represent mutually exclusive cases
- `null` and `undefined` carry business meaning everywhere
- services repeatedly validate the same invariants
- controllers, services, and repositories all throw framework exceptions
- Prisma row types leak into all layers
- booleans encode lifecycle state
- expected business failures are handled via exceptions only

## A minimal house style

If the team wants a simple skill to apply consistently, use this:

1. **Model legal states explicitly**
2. **Use unions before booleans**
3. **Use constructors before ad hoc validation**
4. **Use `Result` for expected business failure**
5. **Use exceptions for defects and technical failures**
6. **Keep Nest and Prisma at the edges**
7. **Pipe pure steps first, effects last**
8. **Prefer small local abstractions over importing a philosophy**

## Final recommendation

If the team asks _“what is the idiomatic FP way in TypeScript/NestJS?”_, a solid answer is:

- use **TypeScript-native algebraic design** first
- keep the **domain explicit and honest**
- use **a small local `Result` and tagged `DomainError` unions**
- introduce a library only when the team wants the whole operating model that comes with it

That keeps the codebase close to TypeScript, close to NestJS, and still faithful to the motto:

**make the illegal state unrepresentable**.
