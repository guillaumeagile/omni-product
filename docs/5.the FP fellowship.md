# The FP fellowship

> Skill: assemble a small set of FP habits — companions, not a framework — that together make tactical DDD code
> always-valid, honestly typed, and cheap to test. General principles, expressed in TypeScript.

## Why a fellowship

No single FP concept delivers good tactical DDD. Immutability without algebraic modeling still allows nonsense states.
`Result` without smart constructors still lets invalid values circulate. Pure functions without explicit effects still
hide I/O in the middle of a decision.

The habits below work as a party: each covers a weakness of the others. The recruiting rule for every member:

**a companion must make the business rule more visible, not less.**

Related reading:

- `4.the FP idiomatic way.md` — the library ladder (TS-native → `neverthrow` → `effect`) and boundary rules
- `agents/rules/typescript-style.md` — the type-system mechanics

## The core party

### 1. Immutability — the constant companion

**Habit**: values never change; every "change" produces a new value.

**DDD payoff**: Value Objects are definitionally immutable. Aggregates whose transitions return new states are
auditable, safe to share, and impossible to corrupt mid-operation.

**TS form**: `readonly` fields, `ReadonlyArray`, `as const`, spread-based updates. The type system is the enforcement —
no `Object.freeze` ceremony required.

```ts
type StockLevel = Readonly<{ productId: ProductId; onHand: Quantity; reserved: Quantity }>;

const reserve = (stock: StockLevel, quantity: Quantity): StockLevel => ({
    ...stock,
    reserved: add(stock.reserved, quantity),
});
```

### 2. Algebraic data types — the map-maker

**Habit**: model with sums (unions) and products (records) so the type describes exactly the legal states — no more, no
fewer.

**DDD payoff**: this *is* "make illegal states unrepresentable". Lifecycles become unions instead of boolean soup; each
state carries only the fields legal in that state.

**TS form**: discriminated unions with a `kind` tag, exhaustive `switch` with a `never` check so new cases fail loudly
at compile time.

```ts
type CatalogItemState =
    | { kind: 'Draft'; name: string }
    | { kind: 'Published'; name: string; slug: Slug; publishedAt: Date }
    | { kind: 'Deprecated'; name: string; deprecatedAt: Date; reason: string };
```

A `Draft` cannot have a `slug`. A `Deprecated` item cannot lack a `reason`. Nobody has to remember — the compiler does.

### 3. Smart constructors — the gatekeeper

**Habit**: trusted types cannot be forged; the only path to a value passes through a constructor that validates.

**DDD payoff**: this is the *always-valid* invariant. If `Price.of(-3)` returns `err(...)`, no invalid `Price` exists
anywhere downstream — so services stop re-checking the same rules.

**TS form**: for a scalar branded value, a private constructor and a static `Result`-returning factory; branded types so
a validated value is not interchangeable with any same-shaped primitive. This is the class shape from
`agents/skills/tactical-ddd-always-valid.md` — objects for models, functions for actions.

```ts
type Brand<T, TBrand extends string> = T & { readonly __brand: TBrand };

class Price {
    private constructor(private readonly amount: Brand<number, 'Price'>) {}

    static of(amount: number): Result<Price, PriceError> {
        return amount >= 0
            ? ok(new Price(amount as Brand<number, 'Price'>))
            : err({kind: 'PriceMustNotBeNegative', amount});
    }
}
```

### 4. Total functions and parse-don't-validate — the translator

**Habit**: a function handles every input its signature admits. Boundary code *parses* raw data into richer types
instead of checking it and passing the raw data along.

**DDD payoff**: the anti-corruption layer in miniature. The DTO dies at the boundary; what crosses inward is a command
in domain vocabulary, and the knowledge gained by validation is stored *in the type*, never re-derived.

**TS form**: Zod `safeParse` → explicit mapper → typed command.

```text
raw payload -> safeParse -> DTO -> map -> ReserveStockCommand (trusted from here on)
```

If a function deeper in the flow re-checks what the type already guarantees, the parse was wasted.

### 5. Functor and monad habits — the pipeline engineer

**Habit**: don't inspect containers, transform through them. `map` when the step cannot fail, `andThen` when it can,
`match` only once at the end.

**DDD payoff**: use cases read as linear business narratives — parse, load, decide, persist — with failures
short-circuiting instead of nesting `if`s. The happy path and every failure path are visible in one place.

**TS form**: the local `Option` module (`src/shared/option.ts`) and `neverthrow`'s `Result`/`ResultAsync`. The habit
matters more than the vocabulary — nobody needs the word "monad" to use `andThen` well.

```ts
const result = await parseCommand(input)
    .asyncAndThen(loadStockItem(repo))
    .andThen(decideReservation)
    .asyncAndThen(persist(repo));
```

### 6. Errors as values — the honest herald

**Habit**: expected business failures are data in the return type. Exceptions are reserved for defects and
infrastructure outages.

**DDD payoff**: the error union of a use case *documents its business rules*. `InsufficientStock | ProductNotFound` is
domain knowledge sitting in a signature; an exception hierarchy hides the same knowledge in scattered `throw` sites.

**TS form**: tagged `DomainError` unions + `Result<T, E>`, mapped to HTTP exactly once at the boundary.

```ts
type ReserveStockError =
    | { kind: 'ProductNotFound'; productId: ProductId }
    | { kind: 'InsufficientStock'; available: number; requested: number };
```

## The support crew

### 7. Pure core, effectful shell — the quartermaster

**Habit**: decisions are pure functions. Effects — database, clock, randomness, network — happen before or after the
decision, never inside it.

**DDD payoff**: aggregates and domain services become trivially testable in memory: load state, call pure `decide()`,
persist the result. This is what turns the workshop's testability goals from aspiration into routine.

**TS form**: pass loaded data *into* domain functions; inject `Clock` and `IdGenerator` as ports; keep Prisma calls in
the first and last lines of the use case.

```text
use case = load (effect) -> decide (pure) -> persist + publish (effect)
```

### 8. Idempotency — the steady hand

**Habit**: applying an operation twice has the same effect as applying it once.

**DDD payoff**: essential for domain event handlers, retries, and sagas — cross-context integration stays safe under
at-least-once delivery. It also pairs naturally with state machines: `archive()` on an already-`Archived` item is an
explicit no-op or explicit error, never silent corruption.

**TS form**: transition functions over the state union that handle *every* source state; deduplication keys on event
handlers.

```ts
const deprecate = (item: CatalogItemState, reason: string, now: Date): Result<CatalogItemState, DeprecateError> => {
    switch (item.kind) {
        case 'Published':
            return ok({kind: 'Deprecated', name: item.name, deprecatedAt: now, reason});
        case 'Deprecated':
            return ok(item); // idempotent: already there
        case 'Draft':
            return err({kind: 'CannotDeprecateDraft'});
    }
};
```

### 9. Closure of operations — Evans' own FP habit

**Habit**: operations whose arguments and return value share the same type — `Money.add(Money): Money`.

**DDD payoff**: straight from the blue book. Value objects compose into small algebras, and the ubiquitous language
*executes*:

```ts
const resellerPrice = supplierPrice
    .plus(margin.appliedTo(supplierPrice))
    .plus(vat.onMarginOnly(margin, supplierPrice));
```

**TS form**: instance methods on the value-object class that stay inside the value-object type — value objects are
classes (see `agents/skills/tactical-ddd-always-valid.md`: objects for models, functions for actions). The smell to
avoid: leaking to raw `number` mid-computation and re-wrapping at the end.

### 10. Equality by value — the twin-spotter

**Habit**: two values with the same content *are* the same thing; identity exists only for entities.

**DDD payoff**: this is the entity / value-object distinction itself, taken seriously. It also removes a whole class of
"same data, different reference" bugs from tests and caches.

**TS form**: `equals()` on value objects; branded typed IDs so a `SupplierId` can never be compared to a `ProductId` by
accident — the compiler rejects the question.

## The one to leave home (mostly)

Type classes, higher-kinded-type emulation, free monads, tagless final. Genuinely FP, genuinely powerful — and in
TypeScript they fight the language and bury the domain under machinery. This is the library ladder from
`4.the FP idiomatic way.md` in disguise: TS-native first, `neverthrow` when the team wants ergonomics, `effect` only as
a deliberate platform decision.

The recruiting rule again: **if a companion makes the business rule less visible, it stays home.**

## How the fellowship maps to tactical DDD

| DDD pattern             | Carried by                                                                 |
|-------------------------|----------------------------------------------------------------------------|
| Value Object            | immutability, smart constructors, closure of operations, equality by value |
| Entity / Aggregate      | ADTs (state unions), smart constructors, pure core, idempotent transitions |
| Domain Service          | total pure functions, functor/monad pipelines                              |
| Domain Event            | errors-and-events as values, idempotent handlers                           |
| Repository (port)       | pure core / effectful shell                                                |
| Anti-corruption layer   | parse-don't-validate, explicit mappers                                     |
| Always-valid invariants | smart constructors + ADTs together                                         |

## The quest

Every member serves the same goal:

**the type signature of a use case should read as a complete, honest statement of a business rule** — what it needs,
what it guarantees, and every way it can legally fail.

```ts
reserveStock(command
:
ReserveStockCommand
):
ResultAsync<StockReserved, ReserveStockError>
```

When a signature reads like that, the fellowship has done its job.
